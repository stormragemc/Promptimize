# Comparison setup and blocked-run recovery

This fix stays on `feature/context-architecture-advisor` / draft PR #3. Main, production and existing frozen candidates remain unchanged.

## What went wrong

The screenshot showed lower candidate input and a reserve below the sample allowance, yet the UI said the input had not reduced or the budget was exceeded. The semantic API had a third blocking condition: unresolved execution context. The UI ignored its `unresolvedCases` and displayed the same generic message for every blocked result.

Investigation verified several integration gaps:

- Preflight used three weighted representative sample requests, while execution displayed six different cases.
- Neither the semantic sample preflight nor its runner supplied structured application state to the selector. Information described in the sentence was not automatically a state field.
- Failed request preparations contributed zero to a partial total, making the candidate look smaller than the complete suite could establish.
- The lookup follow-up appended a tool result without selecting instructions again for the changed state.
- Review findings could block the runtime, but the main-based UI did not expose the backend's explicit conflict-resolution workflow.
- Finding a word such as `status` in prose was enough to accept it as a state-field identifier. That could turn ordinary business wording into an invented executable requirement.

The exact private browser candidate was not available in this session. A source-backed regression fixture reproduces the same missing-state block and verifies the repaired path. Other genuine conflicts or cost increases can still correctly block a particular candidate.

## What changed

`sample-contract.js` supplies the same six cases to the frontend and backend, with explicit fictional state and the state after the successful lookup. These are visible test fixtures, not inferred production facts. Both versions receive the same state in the same request envelope.

Preflight now sizes all 14 bounded requests: six initial cases on both versions plus the lookup follow-up on each version. Its requests are constructed by the same helper execution uses. The follow-up reselects context after the state change. No assistant response is generated by preflight.

When any request cannot be prepared, full totals and the full reserve are unavailable. The API retains known subtotals with clear incomplete flags. Missing requests never become zero-token savings.

The UI displays the exact case, version, stage, missing field or review issue and affected source rules. Test setup is expandable and editable as bounded JSON. Valid edits invalidate sizing and archive prior results without editing the frozen prompt. Invalid JSON blocks a new check. A changed test fingerprint cannot reuse the previous checked request.

The total comparison allowance is editable from 1,000 to 200,000 tokens. Raising it preserves completed results and requires a fresh check; it does not start calls. The 20,000-token per-request limit, output caps, no-input-reduction gate and unresolved-state checks remain enforced.

Source conflicts have a review panel. A person can record an evidence-backed false-positive decision or an affected instruction correction in the next proposal. Context conflicts require corrected project context and reanalysis. The application does not auto-dismiss findings or repair a frozen candidate.

New extraction passes require explicit state identifiers from source/schema/approved state fields rather than accepting arbitrary policy nouns. Unverified interpretations remain source-preserving review findings. Existing frozen routing metadata is not silently rewritten.

## What to do in the preview

1. Open the updated branch preview, select the sample and complete the normal analysis/review/freeze steps.
2. In Tests, click **Check token budget**. All six default sample cases have explicit state; no JSON editing is needed for the supported fixture schema.
3. If a candidate expects another legitimate field, click **Review this test setup**, inspect the source rule, and supply the correct scenario state. The lookup case has separate before/after state.
4. If a proposed field does not exist in the application, use **Reanalyze routing in a next proposal**. Do not invent a value to satisfy the gate.
5. For conflicting rules, create the next proposal and record a source-backed review decision. For a real budget shortfall, adjust the total comparison allowance and check again.

The budget text reports complete instruction-input sizing across the suite, including bounded follow-ups. It is not exact billing or a measured behavioral improvement.
